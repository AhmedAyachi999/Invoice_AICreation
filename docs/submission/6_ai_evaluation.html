AI Invoice Assistant – Evaluation: bot alone vs bot + Python

30 October 2026 · llama3.2:3b (Ollama 0.40.11, OpenAI-compatible API), temperature 0 · tests/test_python.py · result file tests/results/2026-10-30_python.md

Purpose and cases

The AI component understands what the user wants in the chat. The question is how far the language model can be trusted alone, and what Python's protections add. The 20 cases are typical messages of the intended use – a person managing customers, products and invoices – in three groups:

  • control (5): complete, valid requests as a user would type them (change an address, add a customer, mark an invoice paid, …);
  • tricky (12): what goes wrong in real use – missing information ("delete the customer"), wrong values (price "abc", "-4.50", 31/02/2026), records that do not exist ("Nobody Smith", "Flying Carpet", CUS-999);
  • turnover (3): the reports R1–R3 asked in plain English.

Setup

Same 20 cases in two modes, 2 runs per case and mode, a fresh copy of the example data per run. A simulated user types the first message and answers every question of the bot (at most 6 messages).

A – bot alone (INVOICE_PYTHON=off): the bots' answers are used as they are – no forms, no Python checks or corrections.
B – bot + Python: the application as delivered – forms and pickers, Python's checks of every command, the guard against invented records and copied example names, the bot's question instead of a refusal, the delete after a chooser written by Python.

Correct = the task ends with the expected proposal (method, path, values) or with turnover numbers equal to the reports calculated by Python. Nothing is saved without the user's Yes in either mode.

Confidence and uncertainty

The model gives no calibrated confidence, so the application shows no confidence numbers. Two measures handle uncertainty:

  • Validation against rules and the database: every answer of the model is treated as uncertain. Python checks each command against the rules – and against the database whenever it refers to existing records – before the user sees it (record exists? exactly one match? used in invoices? valid date and price?), asks "Which … do you mean?" instead of guessing, and nothing is saved without the user's Yes. This is why B reaches 40/40 while the model alone is wrong in 15 of 40 runs.
  • Agreement across repeated runs: 39 of 40 case/mode pairs gave the same result in both runs. With temperature 0 this shows that the behaviour is stable and repeatable, not that the answers are correct (case 2 was wrong in both runs).

Conclusion

The language model understands complete requests reliably (control and turnover: 16/16 runs alone), but on unclear or wrong input it refuses its task, invents values or crashes (9 of 24 tricky runs correct alone). Python's forms, checks and guards turn all 40 runs into a correct result; nothing is saved without the user's Yes in either mode. Limits: 20 hand-written cases, 2 runs each (temperature 0 makes runs nearly identical), the simulated user's answers are fixed, one model only.
