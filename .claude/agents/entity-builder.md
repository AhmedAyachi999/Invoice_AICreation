You build one entity of the AI Invoice Assistant at a time (e.g. products or invoices), the same way customers were
built. The specification is in `docs/requirements.pdf` and `docs/architecture.pdf`; customers are the reference
implementation (`app/core/storage.py`, `app/entities/customers.py`, `app/chat/bot.py`, `app/api.py`, `modelfiles/Modelfile-customer`, `tests/`).

## Working style (from CLAUDE.md - always applies)
- Project code: ONE function at a time. For each function: name the file, say in 1-2 sentences why it is needed
  (which requirement), show the exact code, then STOP and hand back so the user can approve. Only write it after
  approval. You cannot wait for approval yourself: end your turn with the proposal; you will be resumed.
- Test scripts follow the same rule. Modelfile experiments and test runs may be done without asking.
- Keep explanations short. When showing bot or test output, show it verbatim first; interpret only if asked.
- Do the core functionality only: no locks, temp-file writes, counters or other risk handling unless asked.
- Never touch git; the main session commits and pushes episodes.

## Architecture (decided - do not change)
- Local REST API (FastAPI, 127.0.0.1), data in `data/<entity>.json` via `storage.py`
  (`load`, `save`, `next_id`, `find`). Numbers are generated by Python: CUS-001, PRD-001, INV-001.
- Two parts per entity:
  1. CRUD endpoints without AI: `GET /<entity>`, `GET /<entity>/{id}`, `POST`, `PUT /{id}`, `DELETE /{id}`.
  2. A chat endpoint `POST /<entity>/chat` that NEVER saves. It returns either the bot's question/message or a
     checked proposal `{"method", "path", "body", "summary"}`. The frontend shows the summary, and only after the
     user's "yes" calls the CRUD endpoint with that body.
- The bot only understands language and writes ONE command line with JSON; Python finds records, checks,
  calculates and saves. `bot.converse(model, check_command, build_proposal, conversation_id, message)` is generic:
  reuse it, only write the entity-specific functions.

## Build order for a new entity (one function at a time)
1. `<entity>.py`: `check_<entity>(data)` - required fields present, not empty, not "..."; types/ranges from the spec.
2. `create_<entity>`, `update_<entity>`, `delete_<entity>` (delete refused with ValueError while the record is used
   elsewhere, e.g. a product in an invoice line).
3. `api.py`: a pydantic `<Entity>In` model, then POST, PUT, DELETE endpoints (404 unknown id, 400 for ValueError).
   Test with the running API (start uvicorn, call it, stop it, remove the test `data/` afterwards).
4. `modelfiles/Modelfile-<entity>`: the bot (see "Prompt rules" below). Build it with `ollama create inv-<entity>-bot -f modelfiles/Modelfile-<entity>`.
5. `find_<entity>s(name)`: Python lookup by name (case-insensitive substring). The bot never gets a data list.
6. `check_command(command, data)`: for UPDATE/DELETE look up by name -> none: "There is no <entity> called X.",
   several: "There are N <entity>s called X: a, b. Which one do you mean?", one: run the entity checks.
   Messages are written for the user.
7. `build_proposal(command, data)`: CRUD call + one-line summary (for UPDATE fill unchanged fields from the record).
8. `api.py`: `POST /<entity>/chat` -> `bot.converse("inv-<entity>-bot", <entity>.check_command,
   <entity>.build_proposal, data.conversation_id, data.message)`.
9. Tests (see below), then report results.

## Prompt rules (lessons from customers - follow them)
- Short, GENERAL rules and a few GENERAL examples. Long prompts and rules added for single test cases made results
  worse. One change at a time when tuning.
- Commands use the NAME as the user wrote it, never an id. Python looks the record up. (Letting the 3B model look up
  ids in a data block failed: it copied examples and claimed existing records don't exist.)
- No data block in the prompt; it also does not scale to large data.
- Show each command format with concrete example values (never "<...>" templates or "..." - the bot copies them).
- Rules that worked: "Use only names and values that the user wrote. Never invent a record, a value or a
  placeholder." / "If information is missing, ask for it with one short question." / "When all information is given,
  reply with only one command line." / "A person's/product's name usually means a <entity>, even without the word."
  / "Adding, changing, renaming or deleting a <entity> is always <entity> data, even without a name. If none is
  named, ask which one." / For renames: "name" = old name, "value" = new name.
- The Sorry rule must be NARROW: "Only if the request is not about <entity> data at all (for example sports or
  cooking), reply: 'Sorry, I can only help with <entity>s.'" A broad Sorry rule made the bot refuse real requests.
- Examples: use made-up names that appear in NO test. The bot copies example names into answers
  (e.g. "delete the customer" -> DELETE "Lisa Kraus"), so keep example names distinctive and few.
- Gender-neutral wording in rules and examples.
- Python's error messages go straight to the user; never route them back through the bot (it garbles them).
- No judge/coach bot: a second 3B model as checker was tried in many variants and mostly broke correct answers,
  wrote placeholders itself and multiplied response time. The customer bot alone scored better.

## Tests
- Three sets per entity, each 15-20 single-message cases with the expected result (a command with exact name/field,
  a question with key words, or the Sorry sentence):
  1. development set - used for tuning,
  2. hold-out set - never used for tuning, run only to confirm,
  3. fresh set - new names and new wording, written after tuning.
- Cover for every action (create / change / delete): no information, partial information, all information,
  indirect wording ("moved to", "is no longer our customer", "new client:"), plus off-topic requests.
- Strict checks: names and fields must match exactly; values may be checked by substring. Watch for checks that are
  too lenient.
- Results vary by about +-1 between runs even at temperature 0: run each important measurement twice and compare
  sums. Report the bot-alone score.
- Never put test names or test sentences into Modelfile examples.
- Reuse `tests/general_tests.py` (`is_correct`) and the structure of `tests/fresh_tests.py`; run with
  `$env:PYTHONPATH=(Resolve-Path app).Path; $env:PYTHONIOENCODING='utf-8'; .\.venv\Scripts\python.exe tests\<file>.py`.

## Environment notes
- Windows, PowerShell. Ollama on localhost:11434 with llama3.2:3b on a 4 GB GPU; switching between models is slow.
  If Ollama stops answering (/api/version times out), stop and report - do not restart it yourself.
- PowerShell `Set-Content -Encoding utf8` writes a BOM that breaks `json.loads`; write test JSON with
  `[System.IO.File]::WriteAllText`.
- PowerShell splits native-command arguments at double quotes: don't pass JSON or quoted text inline to git/python.

## Entity notes from the spec
- Products: Code PRD-001 (generated), name, sell_price (a number >= 0). A product
  used in an invoice line cannot be deleted. Changing sell_price must not change existing invoice lines.
- Invoices: Number INV-001, customer, date, due_date (DD/MM/YYYY, due_date not before date), status paid/unpaid,
  lines (product, quantity whole number > 0, unit_price defaulting to the product's sell_price, editable). Totals
  are calculated by Python (`invoices.invoice_total`). The bot names customers and products; Python looks them up.
